# 取消关注 PRD

> 版本: 1.0  
> 更新日期: 2026-01-19

## 背景与问题
当前互关体系已有关注与互关展示，但缺少明确、可验证的“取消关注”产品规范，导致交互、状态流转与数据可见性在实现上不统一。

## 目标
- 为“取消关注”提供清晰的用户流程、状态流转与数据可见性规则。
- 保证取消关注后互关关系立即解除、数据访问立即失效。
- 提供一致的 UI 反馈与错误处理规范，降低误操作与困惑。

## 非目标
- 不引入拉黑/屏蔽能力。
- 不新增新的关注入口，仅覆盖现有页面。
- 不调整后端数据模型（仅定义调用与权限要求）。

## 适用范围
- 页面：关注好友页面。
- 入口：搜索结果列表、互关好友列表。

## 术语与状态
- `following`：我关注对方。
- `follower`：对方关注我。
- `mutual`：双方互关。
- `none`：无关注关系。

## 用户故事
- 作为用户，我可以取消对某人的关注，以停止与对方的互相关注关系。
- 作为用户，我希望取消关注后立刻看不到对方的数据，避免隐私风险。
- 作为用户，我希望系统明确告诉我操作是否成功。

## 交互流程
1. 用户在列表中点击“取消关注”。
2. 系统弹出确认对话框，说明后果（互关解除、数据不可见）。
3. 用户确认后进入加载态；成功后更新列表与状态。
4. 若失败，提示错误并保持原状态。

## 功能需求
### 入口与按钮
- 搜索结果：当状态为 `following` 或 `mutual` 时显示“取消关注”。
- 互关列表：在列表项内提供“取消关注”入口或通过详情操作入口。

### 确认与反馈
- 取消前必须二次确认。
- 操作期间按钮进入 loading 状态，避免重复点击。
- 成功提示为轻提示（如 SnackBar）。
- 失败提示明确原因（如网络错误、权限错误）。

### 状态更新
- 取消成功后：
  - 当前用户对该用户状态变为 `follower` 或 `none`（取决于对方是否仍关注我）。
  - 互关列表中该用户应立即移除。
  - 若当前正在查看对方数据，自动切回“我的”视角，并清空对方缓存数据。

## 数据与权限要求
- 取消关注应删除 `follows` 表中当前用户作为 `follower_id` 的记录。
- RLS 需允许用户删除自己发起的关注记录。
- 取消关注后 `get_follow_status` 与 `get_mutual_follows` 应立即反映新状态。

## 边界与异常
- 重复取消：若关注记录不存在，仍返回成功（幂等）。
- 自关注：禁止取消自身关注请求（视为非法）。
- 网络错误：保持原 UI 状态并提示可重试。
- 并发变化：若对方刚刚取消关注，应以最新状态刷新展示。

## 可见性规则
- 互关被打破后，双方不再互相可见健康数据。
- 任何已加载的对方数据需在 UI 与缓存中清理。

## 埋点与指标
- `unfollow_click`
- `unfollow_confirm`
- `unfollow_success`
- `unfollow_fail`
- 关键指标：取消关注成功率、失败率、平均耗时。

## 验收标准
- 取消关注后互关列表立即移除目标用户。
- 取消关注后无法继续查看对方数据。
- 操作成功/失败均有明确反馈。
- 无重复点击导致的多次请求。

## 依赖与风险
- 依赖 Supabase RLS 与 RPC 及时反映状态。
- 风险：缓存未及时清理导致“已取消仍可见”。需在实现上强制切换视角并清空数据缓存。
